Critical Finding #10 · Infrastructure Security · Prowler OSS

Unrestricted outbound network access

Affected Resource: aws_security_group.cloudguard_open_ssh (prowler_scans/targets/main.tf)
Status: {{ remediation_record.status|default:"PROPOSED" }}

1 What is the problem?

Your security group allows outgoing traffic to any IP address (0.0.0.0/0). This means your cloud resource can communicate with destinations anywhere on the public internet, creating an unnecessary and dangerous exposure.

2 Why should you care?

  • Malicious Command & Control: If an attacker compromises this resource, unrestricted outbound access lets them connect to external attacker-controlled servers.
  • Data Exfiltration: Sensitive files, database dumps, and credentials can easily be uploaded to external internet destinations without restriction.
  • Increased Attack Surface: Unnecessary outbound ports violate the principle of least privilege and fail CIS AWS Benchmark 5.2.

3 What does CloudGuard recommend?

AI Recommendation

Restrict outbound traffic to only the approved destination CIDR and ports required by your application (for example, HTTPS port 443 for package updates and APIs).

Note: The CIDR range (e.g. 10.0.0.0/16) must be confirmed against your actual cloud VPC network topology before applying. AI content is a recommendation, not a guaranteed fix.

4 Review the proposed fix

Before (Insecure) 0.0.0.0/0

Egress rule allows outgoing traffic to all internet destinations on all ports. 

egress {

Expandable Technical Information (For Engineers & Evaluators)

1. Technical Root Cause Breakdown

The AWS Security Group specifies an unrestricted egress rule with protocol = "-1" (all protocols), from_port = 0, to_port = 0, and cidr_blocks = ["0.0.0.0/0"].

In cloud architecture, broad egress violates least-privilege principles and CIS AWS Foundations Benchmark check AWS-0104. Unless explicitly required for a public proxy, security groups must constrain outbound connectivity to verified destination CIDRs and destination application ports (e.g., TCP 443).

2. Threat Model & Attack Scenario

Phase 1: Initial Workload Compromise: An attacker exploits a known web vulnerability (e.g., SSRF or Log4j) on a workload inside this security group.

Phase 2: Egress Beaconing: Because egress is completely unrestricted to 0.0.0.0/0, the compromised host connects outbound to external Command & Control (C2) servers on arbitrary ports without being blocked by network-layer filters.

Phase 3: Data Exfiltration: The attacker transfers customer data or AWS IAM temporary metadata credentials directly out of the account to external endpoints.
